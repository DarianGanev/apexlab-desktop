The adversity corpus asserts all three accounting boundaries:

```text
observed = enqueued + dropped-full + rejected-oversized
source-dequeued = exactly one classifier outcome per dequeued datagram
compatible = written + write-failed + active-pending + deferred-pending
```

It also finalizes evidence and requires every written record to move from staged to finalized accounting.

## Reproduction

Run bounded CI verification (soak excluded):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Verify.ps1
```

Run the opt-in loopback soak with its reviewed minimum:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/CaptureSoak.ps1 -DatagramCount 10000
```

The script accepts 10,000 through 5,000,000 requested datagrams. It writes a TRX result and a privacy-safe JSON summary under ignored `artifacts/test-results/capture-soak/`, then prints the JSON summary. The summary contains only the fixed seed, configured rates, elapsed injection and observation times, aggregate counters, and managed-memory measurements.

Local minimum-soak observation on 2026-08-06:

- requested/observed: 10,000 / 10,000;
- source accounting: 10,000 enqueued, 0 full drops, 0 oversized rejects;
- observed managed-memory growth: approximately 6.0 MiB;
- reviewed ceiling: 128 MiB;
- result: PASS.

This observation is a bounded engineering check, not a throughput claim. The later private F1 25
workflow measured the real peak locally and passed the required at-least-2x gate without committing
the private rate.

After privately measuring the real peak, run a 60-second rate-controlled gate without committing that private value:

```powershell
$realPeak = <privately measured integer datagrams per second>
$targetRate = [math]::Max(167, [math]::Ceiling(2.2 * $realPeak))
$datagramCount = 60 * $targetRate
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/CaptureSoak.ps1 -DatagramCount $datagramCount -TargetDatagramsPerSecond $targetRate -MeasuredRealPeakDatagramsPerSecond $realPeak
```

The script derives the minimum observed rate as exactly 2x the supplied private peak. In rate-gate mode it rejects a target below 110% of that derived minimum, a requested count shorter than 60 seconds at the target rate, or a delivery floor below 95%. The 167-datagram target floor keeps the 60-second command above the script's 10,000-datagram minimum. The gate passes only when at least 95% of requested datagrams reach the source, the measured observed rate meets the derived 2x minimum, source accounting remains exact, ordering is preserved, and managed-memory growth stays within 128 MiB. `TargetDatagramsPerSecond` controls the requested injection pace. The observed-rate clock includes bounded receiver drain time, so delayed loopback delivery cannot be credited at the shorter sender-only duration. The JSON records both durations, the derived minimum, and the achieved send and observed rates. It contains no payload or identifier, remains locally ignored, and must not be committed because the derived minimum reveals the supplied peak by ratio. With the current five-million-datagram cap, rate-gate input supports measured real peaks through 37,878 datagrams per second.

Rate-gate mechanism validation on 2026-08-07 used a synthetic stand-in peak of 70 datagrams per second, not an F1 measurement. The exact documented command derived a 140-datagrams-per-second minimum, sent and observed 10,020/10,020 datagrams at 167 datagrams per second over 60.010 seconds, and passed all accounting and memory assertions. Attempts to configure a 90% delivery floor, less than 10% target headroom, less than 60 seconds, and an infeasible measured peak were each rejected before execution. This proves the gate mechanics independently. The guided private workflow subsequently passed the same enforced mechanism using the privately measured F1 peak; only the safe conclusion is committed in `v0.2.0-private-f125.md`.
