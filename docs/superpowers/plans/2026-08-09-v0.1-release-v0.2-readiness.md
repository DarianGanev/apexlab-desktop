# ApexLab v0.1 Release and v0.2 Readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish the existing v0.1.0 foundation as a verified GitHub release and prepare v0.2.0 as a fully verified release pull request without adding product scope.

**Architecture:** Preserve GitFlow: `release/0.1.0` finishes against `main`, the tagged release is merged back to `develop`, and `release/0.2.0` is then cut from the synchronized integration head. Release evidence records only reproducible commands, immutable GitHub run/tag URLs, package asset names, and the privacy-safe F1 conclusion; raw telemetry and private rates never enter Git.

**Tech Stack:** Git/GitHub CLI, PowerShell 5.1, .NET SDK 10.0.302, WPF/.NET self-contained `win-x64` publishing, GitHub Actions.

## Global Constraints

- Work only in isolated worktrees; preserve the existing `release/0.1.0` worktree until v0.1.0 is published and merged back.
- Use the repository owner's configured Git identity and semantic version tags `v0.1.0` and `v0.2.0`.
- Do not commit telemetry payloads, capture identifiers, hashes, paths, sender/session identifiers, or exact private rates.
- Do not claim a clean-machine or SmartScreen observation that was not actually performed.
- Treat a runtime-isolated packaged smoke test as additional self-contained evidence, not as a substitute for the roadmap's definitive clean-machine gate before v1.0.
- Every release candidate must pass `scripts/Verify.ps1`, `scripts/Publish.ps1`, and `scripts/SmokeTest.ps1` from a clean worktree before it is pushed.
- v0.2 preparation may update release metadata and evidence only; no new product feature enters the release.
