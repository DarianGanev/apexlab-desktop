# Manually audited comparable Bahrain laps design

**Date:** 2026-08-09
**Issue:** #27
**Status:** Approved for implementation
**Version identity:** `bahrain-tt-lap-audit-v1`

## 1. Outcome

ApexLab will turn one verified canonical replay into an inventory of provisional lap candidates, bind
each candidate to exact local evidence, require a human audit decision for every candidate, and
select a baseline only when at least five included laps share one frozen Bahrain Time Trial context.

The workflow is intentionally conservative. It does not claim to implement the general lap state
machine scheduled for v0.5. Direct contradictions can prevent inclusion, but no inferred signal can
silently mark a lap clean. Fewer than five comparable laps produces an explicit abstention.

## 2. Scope

The implementation includes:

- deterministic provisional boundary extraction from verified canonical records;
- explicit leading/trailing/incoherent partial candidates;
- direct evidence flags for invalidation, pit presence, flashback, material gaps, context changes,
  unsupported context, and player-index changes;
- a versioned local-only audit document with one decision per candidate;
- exact comparison-context matching for the supported Bahrain Time Trial slice;
- bounded manual confirmations for game build, vehicle, controller profile, setup, and tyre;
- a five-lap baseline threshold with typed abstention reasons;
- handle-safe local persistence for the audit document;
- production prepare and validate commands;
- privacy-safe aggregate validation output; and
- fixed synthetic and private replay evidence.

The implementation explicitly excludes:

- automatic clean-lap classification;
- a complete invalidation/restart/pause/flashback/pit state machine;
- cross-session automatic selection;
- a generalized context fingerprint;
- setup, status, damage, or time-trial packet expansion;
- trace visualization or an audit GUI;
- one-metre alignment, reference selection, delta, findings, or coaching; and
- database schema changes.

The local audit document is the provisional product input for v0.3. Review UI work in #32 may edit
the same contract later. SQLite metadata is deferred until the session library is designed rather
than introducing a premature schema around a deliberately provisional workflow.

## 3. Trust and privacy model

Raw evidence remains authoritative. The canonical cache is trusted only after the existing strict
reader has verified its structure, accounting, source/version identity, data checksum, and canonical
checksum. An audit document is never sufficient by itself.

The audit document is private application data. It contains local evidence identities, candidate
identities, boundary sequences, lap numbers, official lap times, context values, setup descriptors,
and optional factual notes. It is ignored by Git and never printed by production commands.

Console validation output is a closed safe schema. It may contain only:

- schema and algorithm version identifiers;
- categorical status and conclusion;
- included, excluded, and pending candidate counts;
- Boolean audit, context, threshold, determinism, provenance, and privacy gates.

It must not contain capture or candidate identifiers, hashes, paths, filenames, session/frame/source
sequences, lap numbers or times, context values, setup text, notes, coordinates, or telemetry.

## 4. Layering

### Domain

`ApexLab.Domain` owns immutable lap-audit and baseline-selection concepts:

- candidate identity and half-open source boundary;
- boundary completeness;
- direct evidence flags;
- manual decision and factual exclusion reason;
- frozen manual comparison context;
- audited candidate;
- baseline disposition and abstention reasons; and
- the pure baseline selector.

Domain code has no filesystem, JSON, database, telemetry, clock, or command-line dependency.

### Application

`ApexLab.Application` owns the provisional Bahrain assembler and use case. It reads canonical records,
creates deterministic inventory candidates, derives telemetry context snapshots, validates an audit
against the exact inventory and canonical identity, and invokes the pure selector.

### Persistence

`ApexLab.Persistence` owns the strict audit JSON codec and handle-safe local store. Audit documents
live beneath `ApplicationPaths.LapAuditsDirectory`. Publication uses a newly created staging leaf,
durable flush, non-overwriting rename, and final re-open verification. Existing audit files are never
silently replaced.

### Replay tool

`ApexLab.Replay` is the composition root for two production commands:

- `prepare-bahrain-lap-audit --data-root <absolute-root> --capture-id <id>`
- `validate-bahrain-lap-audit --data-root <absolute-root> --capture-id <id>`

Prepare creates the deterministic template at its fixed application-data location. Validate rebuilds
or verifies the canonical cache, reads the exact audit document, evaluates it, replays independently
for determinism, and prints only the safe report.

## 5. Candidate boundary model

A candidate uses a half-open evidence interval:

```text
[start source sequence, completion source sequence)
```

The completion Lap Data observation supplies the completed lap's official time and is stored as a
separate completion-evidence sequence. This avoids overlapping adjacent lap intervals while retaining
the exact record that proves completion.

The assembler recognizes a provisional completed boundary only when:

1. a positive current-lap number has been observed;
2. a later Lap Data observation advances it by exactly one;
3. the transition reports a positive last-lap time; and
4. start, completion, and source ordering remain representable.

The first observed lap is leading-partial until a prior transition established its start. The open lap
at end of replay is trailing-partial. Jumps, regressions, duplicate transitions, missing completion
times, or exhausted sequence ranges close the affected inventory entry as incoherent/incomplete; they
do not fabricate a completed lap.

Every candidate identity is a lowercase SHA-256 over a domain separator plus length-delimited:

- canonical identity digest;
- lap-audit version;
- boundary kind and source boundaries;
- completion-evidence sequence when present;
- observed lap number and official time when present; and
- the deterministic direct-evidence flag mask and telemetry-context digest.

No wall-clock time, random identifier, path, or collection order enters the identity.

## 6. Direct evidence flags

The assembler records facts; it does not make the audit decision. Flags are accumulated inside the
candidate boundary:

- `InvalidationObserved`: a Lap Data observation marks the current lap invalid;
- `PitObserved`: a Lap Data observation reports a non-zero pit status;
- `FlashbackObserved`: a selected flashback event occurs;
- `MaterialGapObserved`: consecutive retained canonical observations are more than one second apart while the interval is active. Canonical source-sequence gaps remain preserved for coverage analysis, but a gap caused only by an intentionally unretained/privacy-excluded datagram is not itself a material telemetry discontinuity;
- `ContextChanged`: the selected Session context changes during the interval;
- `UnsupportedContext`: the selected context is not the frozen offline Bahrain Time Trial context;
- `PlayerIndexChanged`: a selected packet changes player or secondary-player index; and
- `MissingContext`: no complete supported Session snapshot governs the interval.

An included decision is invalid when any direct contradiction flag is present or the candidate is not
complete. This is a fail-closed consistency rule, not an automatic validity classifier. A complete,
unflagged candidate still remains pending until a human explicitly includes or excludes it.

## 7. Frozen comparison context

Telemetry context is exact for the provisional slice and includes all selected Session fields plus
player/secondary-player indices. Supported constants must match the frozen contract:

- track 3 (Bahrain);
- game mode 5;
- session type 18;
- rule set 2;
- offline network flag;
- not spectating;
- player index 0 through 21; and
- secondary player index 255.

Weather, temperatures, track length, formula, assists, time of day, equal-car performance, and
recovery mode are also retained and compared exactly. Exact matching is deliberately conservative;
the provisional slice adopts no undocumented tolerance.

The manual context requires bounded non-empty values for game build, player vehicle, controller
profile, setup descriptor, and tyre compound. It also requires affirmative evidence-integrity,
track/mode visual confirmation, setup-unchanged, and context-cross-check confirmations. Missing or
false confirmations cause abstention and cannot be converted to inclusion by a lap decision.

## 8. Audit contract

The prepared JSON document is closed, versioned, deterministic, UTF-8 without BOM, and ends with one
newline. It contains:

- schema version and `lapAuditId`;
- canonical identity and canonical checksum;
- the generated telemetry reference context;
- the manual comparison context fields;
- every inventory candidate in deterministic order; and
- one nullable decision plus nullable reason/note per candidate.

Prepare writes all decisions as `null`. The user must set each to `included` or `excluded`. Excluded
candidates require one frozen reason:

- `invalidated`;
- `pit-entry-or-exit`;
- `flashback-observed`;
- `material-gap`;
- `context-mismatch`;
- `incomplete-lap`; or
- `other-factual`.

`other-factual` requires a trimmed, bounded local note. Other reasons forbid a note. A direct reason
must agree with the corresponding evidence flag or boundary state. The exact inventory set, order,
identities, boundaries, evidence flags, and telemetry context must match a newly assembled replay.
Duplicates, omissions, additions, stale identity, unknown properties, unknown enum values, excessive
length, malformed JSON, or contradictions fail closed.

Prepare refuses to overwrite an existing document. This protects manual work. If evidence or an
algorithm version changes, the stale document is rejected; the user must deliberately preserve or
remove it before preparing a new audit.

## 9. Baseline selection and abstention

The pure selector has a frozen minimum of five included candidates. `Ready` requires:

- exact audit/inventory agreement;
- every candidate manually decided;
- all global manual confirmations true;
- every included candidate complete and free of direct contradictions;
- every included candidate matching the one telemetry and manual context; and
- at least five included candidates.

Otherwise the result is `Abstained` with one or more ordered categorical reasons:

- `AuditIncomplete`;
- `ContextNotConfirmed`;
- `ContextMismatch`;
- `ContradictoryIncludedLap`; or
- `InsufficientComparableLaps`.

Malformed or dishonest audit data is an input error, not an abstention. An abstention describes valid
evidence that is insufficient for coaching.

## 10. Determinism gate

Synthetic tests use fixed canonical records and fixed manual values. Two independent assemblies of
the same records must produce byte-identical templates and identical selection results. Mutating the
canonical identity, audit version, a boundary, a context value, decision, or reason must change or
invalidate the appropriate identity/result.

The private validation command independently opens/replays the same private capture twice and checks:

- identical candidate identities and template bytes;
- exact audit agreement with both inventories;
- every candidate decided;
- exact context match for every included lap;
- factual reasons for every excluded lap;
- at least five included baseline laps; and
- private-data exclusion from the safe report.

If fewer than five comparable laps exist, the command exits with a distinct abstention code and safe
`ABSTAIN` conclusion. It must never relabel abstention as a passing baseline gate.

## 11. Failure and ownership rules

- Cancellation propagates through replay, assembly, persistence, and validation.
- Sources, cache entries, streams, directory handles, and temporary resources have one explicit owner.
- Primary and cleanup failures are preserved together.
- Audit publication never overwrites an existing final leaf.
- Reparse directories, reparse files, hard-linked files, traversal, alternate data streams, device
  names, and unexpected final handle paths fail closed.
- Validation exceptions are mapped to closed categorical output; raw exception messages are not
  emitted by production commands.

## 12. Test strategy

Tests must cover:

- all value-object bounds, enum values, and conditional audit invariants;
- completed, leading-partial, trailing-partial, jump, regression, and missing-time boundaries;
- each direct evidence flag and combined flags;
- supported and unsupported contexts and exact context changes;
- stable and changing player indices;
- deterministic identity and inventory ordering;
- strict one-to-one audit/inventory agreement;
- all exclusion-reason consistency rules;
- four included laps abstaining and five becoming ready;
- ready selection remaining independent of input collection order where ordering is not semantic;
- strict JSON duplicate/unknown/missing/oversized/malformed cases;
- non-overwriting durable publication and handle release;
- reparse/hard-link rejection;
- production command parsing, safe schema, exit codes, cancellation, and error sanitization;
- fixed-seed end-to-end replay; and
- private aggregate validation without publishing private values.

## 13. Completion criteria

Issue #27 is complete only when:

1. every included synthetic and private lap has an explicit human audit and exact context match;
2. every excluded lap has one factual, contract-valid reason;
3. four comparable laps deterministically abstain and five deterministically become ready;
4. the private command reports aggregate included/excluded counts and a truthful threshold result;
5. private paths, identities, times, numbers, context, setup, notes, and telemetry remain outside Git
   and console output; and
6. exact-head verification, package, smoke, PR CI, and merge-commit CI all pass.
