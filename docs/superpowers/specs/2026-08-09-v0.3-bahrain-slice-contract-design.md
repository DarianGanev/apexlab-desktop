# v0.3 Bahrain Slice Contract Design

**Status:** Approved under the owner's standing instruction to make routine engineering decisions
without pausing for plan approval.

**Issue:** [#24](https://github.com/DarianGanev/apexlab-desktop/issues/24)

## Objective

Freeze a reviewable, versioned boundary for the first ApexLab coaching vertical slice before packet
decoding or analysis implementation can drift. A reviewer must be able to trace every downstream
v0.3 requirement to protocol metadata, units, local-only D1 inputs, version identifiers, and a
commit-safe evidence result without inspecting private telemetry.

This contract is an engineering preregistration for the slice. It does not assert that the selected
detector is accurate, that an instruction improves driving, or that results generalize beyond the
owner's provisional Bahrain evidence.

## Selected approach

Three approaches were considered:

1. A prose-only contract is easy to read but cannot prevent offset, allowlist, or traceability drift.
2. A human-readable specification plus a machine-readable contract and executable invariant tests
   keeps intent understandable while making the critical boundary mechanically reviewable.
3. Production domain types would provide compile-time coupling but would prematurely implement the
   decoder, analysis, and experiment issues that follow this one.

Approach 2 is selected. It provides technical evidence appropriate for a diploma project while
preserving the dependency order in issues #25 through #34.

The attachments remain ignored under `vendor-specs/` and are never copied into Git. The committed
contract is independently authored metadata derived from their published field definitions. The
PDF appendix was visually checked for the frozen enumeration values.

## Supported input boundary

The contract ID is `apexlab-bahrain-tt-slice-v1`. It accepts only:

| Property | Required value |
| --- | --- |
| Adapter | `ea-f1-25-v3` |
| Packet format | `2025` |
| Game year | `25` |
| Packet version | `1` for each selected family |
| Track | Sakhir (Bahrain), `trackId = 3` |
| Game mode | Time Trial, `gameMode = 5` |
| Session type | Time Trial, `sessionType = 18` |
| Ruleset | Time Trial, `ruleSet = 2` |
| Network mode | Offline, `networkGame = 0` |
| Player selection | Stable `playerCarIndex` in `[0, 21]` |
| Secondary player | Absent, `secondaryPlayerCarIndex = 255` |
| Spectating | Rejected |
| Source evidence | One integrity-verified v0.2 raw capture, replayed locally |

The slice reads only the player array entry selected by the validated packet header. Anonymous
other-car entries may remain inside the private raw datagram, but they are neither decoded into the
v0.3 canonical cache nor exported by the safe result.

## Selected packet fields

The machine-readable contract records exact packed offsets, types, units, array strides, and issue
consumers. The human-level selection is:

- **Header:** format/year/version/family identity; private session correlation; session time; frame
  and overall-frame identifiers; player and secondary-player indexes.
- **Session:** weather and temperatures; track length; session type; track ID; formula; spectating
  and network state; published assist settings; game mode; ruleset; time of day; equal-car setting;
  recovery mode.
- **Lap Data, player entry:** last/current lap time; lap and total distance; lap number; pit status;
  sector; invalid flag; driver status; result status.
- **Motion, player entry:** world X/Y/Z position for reviewed local corner/landmark evidence.
- **Car Telemetry, player entry:** speed, throttle, brake, and gear for the provisional braking
  finding, adherence measure, and guards.
- **Event:** four-byte event code plus Flashback target frame and target session time for `FLBK`.
  The no-detail `SSTA` and `SEND` codes are recognized as session evidence.

Steering, RPM, setup packets, tyre/status/damage packets, generalized event details, full track
geometry, and complete packet models are deliberately deferred. A downstream implementation may
not decode an extra field under this contract merely because it is convenient; the contract must be
versioned first.

## Local-only D1 audit inputs

The five packet families cannot prove every comparability fact. A local audit record therefore must
capture these facts before a lap is eligible:

- evidence identity and integrity result;
- game-build label and adapter ID;
- visual confirmation of Bahrain Time Trial and the player vehicle;
- wheel controller class;
- setup descriptor and explicit confirmation that it did not change across selected laps;
- cross-check of assists, equal-car setting, conditions, and recovery/flashback policy;
- per-lap inclusion or factual exclusion decision;
- selected corner-revision and driver-visible-landmark review identifiers.

Actual values, evidence identities, lap decisions, and notes remain in local application data. Git
may contain only the input field definitions and aggregate pass/fail conclusions.

## Committed artifacts

The implementation produces:

1. `contracts/v0.3/bahrain-slice-v1.json`: exact protocol source identities, supported context,
   packet field layout, manual-input definitions, version IDs, and issue traceability.
2. `contracts/v0.3/bahrain-safe-summary-v1.schema.json`: a closed JSON Schema for the only v0.3
   private-gate conclusion allowed to enter Git.
3. `docs/contracts/v0.3-bahrain-slice-v1.md`: reviewer-oriented interpretation, non-claims, and
   field-to-requirement tables.
4. `BahrainSliceContractTests`: executable structural, bounds, traceability, and privacy-allowlist
   invariants over both machine-readable files.

Production code does not load repository documentation at runtime. Later implementation tests may
cross-check decoder constants against the frozen contract, but runtime artifacts own their own
versioned types.

## Safe result boundary

The safe-summary schema is closed with `additionalProperties: false`. It contains only:

- schema/status/date and bounded game-build metadata;
- the exact non-personal version identifiers above;
- booleans for the minimum-baseline, deterministic-replay, provenance, and private-data gates;
- categorical finding disposition and experiment outcome;
- final `PASS` or `FAIL`.

It forbids raw payloads, capture/manifest/source hashes, session or frame identifiers, sender data,
paths, usernames, lap or segment times, exact counts above the declared minimum, exact rates,
coordinates, setup values, and free-form notes. Exact source-chunk hashes still support local claims;
the committed result records only whether provenance was complete.

## Failure handling

The slice rejects or abstains when the context constants do not match, the player index is invalid or
changes, required fields are malformed or non-finite, selected evidence has material gaps, the local
audit is incomplete, fewer than five comparable baselines survive audit, or provenance cannot be
resolved. It never substitutes defaults for an unknown required value.

`NotFollowed` remains distinct from `Rejected`. An abstention or incomplete experiment can be
represented by a safe failing summary, but cannot satisfy the v0.3 release gate.

## Explicit non-scope and non-claims

- No generalized track, session, setup, or lap-validity system.
- No automatic claim that a lap is clean beyond the frozen provisional checks and manual audit.
- No production recorder compression, recovery, rotation, indexing, or library behavior.
- No multi-track or multiplayer support.
- No machine learning, generative advice, chatbot, or cloud processing.
- No coaching-effectiveness, expert-equivalence, population, or causal claim.
- No public fixture derived from real telemetry and no vendor attachment in source control.

## Acceptance evidence

The issue is complete only when the machine-readable artifacts parse strictly, invariant tests prove
field bounds and traceability, the safe schema contains exactly the allowlisted properties, all tests
pass, and a reviewer can follow every downstream issue to a frozen requirement without private
evidence.
