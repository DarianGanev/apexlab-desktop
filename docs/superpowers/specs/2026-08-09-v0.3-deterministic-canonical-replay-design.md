# v0.3 Deterministic Canonical Replay Cache Design

**Status:** Approved for implementation

**Date:** 2026-08-09

**Issue:** [#26](https://github.com/DarianGanev/apexlab-desktop/issues/26)

## Objective

Replay one integrity-verified v0.2 F1 25 evidence capture into the minimal, deterministic canonical
stream required by the frozen Bahrain Time Trial slice. Identical evidence and version identities
must produce an identical canonical checksum. Filtered inputs and source-sequence discontinuities
must remain explicit records. A local derived cache may accelerate later work, but raw evidence
remains authoritative and any missing, stale, malformed, or corrupt cache is rebuilt.

This issue establishes chronology, provenance, canonical representation, and cache integrity. It
does not decide lap validity, join samples into laps, interpolate channels, compare attempts, or make
a coaching claim.

## Considered approaches

### 1. Persist decoded packets as ordinary JSON

This is easy to inspect, but it makes byte-for-byte determinism depend on property order, serializer
configuration, runtime floating-point formatting, and whitespace. It also encourages downstream
code to treat an editable derived file as authoritative. JSON remains appropriate for a small local
manifest, not for the canonical sample stream.

### 2. Write one SQLite row per telemetry value

SQLite would provide convenient queries and transactions, but high-frequency row storage is outside
the repository's architecture: the database owns metadata and derived indexes, not every sample.
Introducing schema migrations, indexes, and per-value rows in this provisional slice would add
write amplification while obscuring the deterministic byte stream the issue must prove.

### 3. Deterministic binary stream plus integrity-bound manifest

The selected design writes an explicitly versioned little-endian binary stream and a closed JSON
manifest. Floating-point values are stored by their exact IEEE 754 bit patterns. Record order is
source order. A SHA-256 checksum binds the canonical bytes to the complete source-and-version
identity. The cache uses staging files and handle-safe replacement; a reader validates structure,
limits, identity, and digests before returning a hit.

This option produces the strongest reproducibility evidence, keeps later analysis independent of
F1 wire layouts, and makes derived-data trust rules executable without introducing the deferred
production chunking or database model.

## Dependency ownership

The implementation preserves the existing inward dependency graph:

- `ApexLab.Telemetry.Abstractions` owns infrastructure-neutral canonical record and projection
  contracts;
- `ApexLab.Protocols.F125` projects the five frozen decoder results into canonical packet values;
- `ApexLab.Application` owns ordered replay, explicit gap insertion, exclusion handling, cache-hit
  policy, and source/writer lifecycle;
- `ApexLab.Persistence` implements the local deterministic binary cache and verified raw replay
  input factory;
- `ApexLab.Replay` composes the same workflow for private validation; it does not duplicate the
  projection or cache algorithm.

No pure project gains a filesystem, SQLite, socket, WPF, or wall-clock dependency. No production
project references the replay tool or a test project.

## Frozen identities

The cache identity contains exactly these canonical strings:

| Component | Identity |
| --- | --- |
| Source evidence | verified lowercase SHA-256 from the finalized v0.2 manifest |
| Protocol | `ea-f1-25-v3` |
| Slice contract | `apexlab-bahrain-tt-slice-v1` |
| Decoder | `f125-v3-minimal-decoder-v1` |
| Canonical schema | `apexlab-canonical-sample-v1` |

The source capture ID, local path, creation time, and application version do not affect canonical
content identity. Two local copies of identical verified evidence therefore produce the same result.
Every component is length-framed before hashing, so concatenation ambiguity is impossible.

The identity digest selects the local cache leaf name. Changing any version selects a different
entry and cannot return the old entry. A cache manifest must exactly equal the requested identity;
filename agreement alone is never trusted.

## Canonical record model

The stream contains three record kinds.

### Observation

An observation retains source chronology and one selected canonical payload:

- positive source sequence;
- non-negative raw monotonic arrival timestamp, with the source stopwatch frequency stored in the
  manifest;
- finite F1 session time in seconds;
- frame identifier and overall frame identifier;
- validated player-car index and secondary-player index;
- one family discriminator and exactly one typed family payload.

The five payloads preserve the fields and units frozen by
`apexlab-bahrain-tt-slice-v1`: Motion metres, Session context and assists, Lap Data milliseconds and
metres, selected Event state, and Car Telemetry kilometres per hour/ratios/signed gear. The
canonical API does not expose a raw payload, sender, wall-clock receive time, session UID, or values
for other cars.

### Exclusion

Every retained compatible input that is intentionally outside the canonical slice produces an
exclusion record instead of disappearing. It contains source sequence, packet ID, and one bounded
reason:

- `CompatibleFamilyOutsideSlice`; or
- `EventCodeOutsideSlice`.

Malformed, unsupported, privacy-excluded, or otherwise rejected input is not an exclusion. It
faults the build, publishes no completed cache, and returns a bounded failure.

### Gap

Before processing an envelope whose sequence is greater than the previous sequence plus one, the
workflow writes one gap record containing the inclusive missing sequence range. A first retained
sequence greater than one produces a leading gap. Duplicate or decreasing sequences fault the
build. No trailing gap is invented because the evidence does not prove what followed its final
record.

The gap reason is `UnretainedOrMissingSourceRange`. The v0.2 evidence format cannot distinguish
network loss from packets rejected or privacy-excluded before persistence, so the canonical layer
must not claim a cause it cannot prove. No interpolation or default sample is generated.

## Projection semantics

`F125BahrainCanonicalProjector` first uses the same structural adapter and typed decoder introduced
by #25. Selected families map only after a `Decoded` result. An ignored Event becomes an explicit
Event exclusion. Other structurally compatible, evidence-allowed families become explicit family
exclusions. Any decoder rejection or incompatible input returns a categorical rejection with no
partial canonical value.

The projector publishes and self-checks the protocol, contract, decoder, and canonical schema IDs.
The Application workflow requires exact equality between those IDs, the source identity, and the
cache request before starting replay.

## Binary data format

The data file is `APXCAN1` format version 1:

1. a fixed header with magic, data-format version, header length, and source stopwatch frequency;
2. ordered length-framed records;
3. a fixed footer containing record accounting and the first/last source sequence when present.

All integers use little-endian encoding. Boolean values use exactly `0` or `1`. Floats use their
validated finite `Single` bit pattern. Nullable Event union values use an explicit presence byte.
Every record length and discriminator is checked before a reader advances. Absolute file, record,
and manifest limits prevent unbounded allocation or length arithmetic.

The binary file contains no version text or source digest; those belong to the manifest. The
canonical checksum is SHA-256 over a domain separator, the length-framed full identity, and the
complete finalized binary bytes. The manifest separately stores the raw data-file SHA-256 for
integrity diagnosis. Thus version changes alter canonical identity even if selected values happen
to serialize to the same bytes.

## Manifest and cache lifecycle

The local JSON manifest has a closed property set and deterministic property order:

- manifest/data format versions;
- identity digest and all five identity components;
- content-addressed data leaf name and data length;
- data SHA-256 and canonical SHA-256;
- source stopwatch frequency;
- canonical record count and observation/exclusion/gap accounting;
- first and last source sequence, nullable for an empty stream.

No wall-clock field is written, so two independent builds have identical finalized bytes and
manifests. Counts and digests are local-only and never enter a commit-safe result.

The cache workflow is:

1. open and integrity-check raw evidence;
2. compute and validate the requested identity;
3. attempt a verified cache read;
4. on a valid exact-identity hit, return its completion without starting replay;
5. otherwise create uniquely named staging data and manifest files;
6. replay, project, insert gaps, write records, finalize, flush, and hash;
7. publish the content-addressed data leaf first, then atomically publish the manifest as the sole
   authority boundary only after every check passes;
8. reopen and verify the manifest-selected entry before returning it.

The data leaf includes both the identity digest and data digest. An unpublished data leaf is inert
because readers resolve data only through a verified manifest. Cancellation or failure stops and
disposes the exact source/writer ownership boundary and removes only its staging leaves. Existing
valid final cache files remain authoritative until a replacement manifest is ready. Orphan cleanup,
production chunking, quotas, and general startup recovery remain deferred.

If a final entry is malformed, corrupt, over-limit, or identity-mismatched, it is treated as a miss.
The workflow rebuilds from verified raw evidence and never supplies stale samples to a consumer.
If replacement cannot be completed, the build fails safely rather than returning the invalid entry.

## Result and failure model

The Application result reports whether the entry was built or reused and returns an immutable local
completion containing identity and integrity metadata. Failures are typed and bounded:

- source protocol or identity mismatch;
- projection rejection;
- duplicate or reordered source sequence;
- cache read/format/integrity failure followed by rebuild failure;
- interrupted replay;
- storage or resource failure.

Exception messages and local identity values are never copied into public safe JSON. Cleanup
failures remain causally attached for local diagnostics.

## Private verification command

`validate-canonical-replay --data-root <absolute> --capture-id <id>` opens the retained evidence and
performs two forced builds in separate temporary local cache roots. It compares canonical checksums,
data checksums, accounting, and manifests; it also proves a deliberately version-mutated lookup
cannot reuse the first entry. Temporary derived files are deleted after handles close.

The command emits a closed allowlisted report containing only:

- schema version and `canonical-replay-validation-v1`;
- status;
- protocol, contract, decoder, and canonical schema IDs;
- `deterministicReplay`;
- `explicitGapPolicy`;
- `staleCacheRejected`;
- `privateDataExcluded`;
- `PASS` or `FAIL`.

It never serializes source/cache digests, capture IDs, paths, counts, rates, timestamps, session or
frame identifiers, packet IDs, decoded values, exception text, or temporary names.

## Test strategy

### Contract and canonical model

- exact production IDs remain equal to the frozen Bahrain JSON;
- constructors reject unspecified kinds, ambiguous unions, non-finite values, invalid booleans,
  malformed identities, and impossible sequence ranges;
- public canonical property names remain unit-bearing and contain no raw transport/storage surface.

### F1 projection

- independent packets map every selected field and exact float bit pattern;
- selected Events, ignored Events, and compatible non-slice families produce their exact result;
- every structural/field rejection remains fail closed;
- fixed-seed arbitrary datagrams never throw or return an unspecified disposition.

### Application workflow

- input order is preserved;
- leading and interior gaps are explicit and exact;
- exclusions remain ordered records;
- duplicate/reordered sequences and rejected projections publish no completion;
- exact cache hits do not start the source;
- version changes and invalid cache reads rebuild;
- cancellation and writer/source failures release every owned resource.

### Persistence

- golden bytes verify header, record, footer, little-endian, signedness, float bits, and nullable
  Event unions independently of the production reader;
- two independent writes produce identical data, manifest, and canonical checksums;
- truncation, trailing bytes, unknown versions/kinds, malformed lengths, digest mismatch, accounting
  mismatch, identity mismatch, unsafe paths, and reparse/hard-link cases fail closed;
- publication and cleanup tolerate injected failures without deleting unrelated or valid files.

### Integration and private evidence

- fixed-seed synthetic evidence proves build, hit, invalidation, rebuild, explicit gaps, and checksum
  stability through the real decoder/workflow/store boundary;
- two independent private replays return the same closed safe PASS conclusion;
- the full repository, package, and smoke gates pass on the exact PR and merge heads.

## Explicit non-scope and non-claims

- No compression, five-second chunks, SQLite sample rows, quota management, startup recovery, import,
  export, or general session library.
- No live canonicalization path, WPF cache browser, background processing, or cross-machine sync.
- No lap construction, context match, validity decision, resampling, interpolation, deduplication,
  flashback policy, reference selection, delta, detector, experiment, AI, or coaching conclusion.
- No support outside base F1 25 v3 and the frozen private Bahrain Time Trial engineering slice.
- No raw or canonical private data, source/cache digest, manifest, or generated fixture derived from
  the owner's capture enters Git.
